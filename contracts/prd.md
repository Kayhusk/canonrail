# Product requirements contract

A PRD defines the user problem, desired outcomes, scope, and acceptance.
It does not present implementation choices as settled decisions.

## Owns

- The problem and the people affected by it.
- User outcomes and the evidence that would show improvement.
- Included and excluded scope.
- Product, legal, privacy, accessibility, and operational constraints.
- Acceptance criteria stated as observable behavior.

## Must not absorb

- Architecture or technology choices unless the requirement depends on them.
- Internal agent workflows, prompts, tool history, or review conversations.
- Invented metrics, deadlines, users, limits, or market claims.
- A task breakdown that belongs in tickets or an execution plan.
- Approval or launch status not supported by the current owner.

## Review

- Trace every requirement to user evidence, a binding constraint, or an explicit decision.
- Label assumptions and unresolved questions.
- Check that acceptance measures outcomes rather than file changes.
- Remove implementation detail that does not constrain the product.
- Use one term for each concept throughout the document.
